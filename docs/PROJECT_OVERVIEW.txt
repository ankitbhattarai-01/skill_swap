1. EXECUTIVE SUMMARY
================================================================================

SkillSwap Connect is a full-stack peer learning marketplace for students.
Learners discover peers by skill, book sessions, chat, meet over embedded
video, and exchange value through an internal CREDIT ECONOMY instead of cash.

The codebase is built as a production-oriented student innovation project:
  - Strong database-side business rules (110+ SQL migrations)
  - Enterprise-style admin tooling (RBAC, finance, compliance)
  - Compliance-oriented documentation in docs/compliance/
  - Security-first Cloudflare Worker edge (CSP, HSTS, etc.)

Workspace layout:
  - skillswap-connect/  — Full application (all product code)

================================================================================
2. PRODUCT VISION & VALUE PROPOSITION
================================================================================

Audience:     Students who teach what they know and learn from peers
Monetization: Credits only — no credit card for core flows
Starter:      10 starter credits (configurable via feature flags)
Core loop:    Discover → Request → Accept → Schedule → Video → Complete → Credits

Differentiators:
  - Built-in Jitsi video (meet.jit.si or 8x8 JaaS)
  - Session-linked messaging
  - Learning tracks (multi-session paths)
  - AI suggestions (optional, Gemini-grounded)
  - Strikes, reports, moderation
  - Enterprise admin console with RBAC and separation of duties

Landing page workflow (marketing):
  Request  — Choose a skill and send a session request
  Accept   — Teachers approve, schedule, and open the video room
  Learn    — Chat, meet, complete, and transfer credits

Feature pillars on landing page:
  - Find peer teachers (browse by skills, level, rating)
  - Exchange with credits (earn by teaching, spend to learn)
  - Learn face-to-face (embedded Jitsi video room)

Proof points:
  - No credit card
  - 10 starter credits
  - Built-in video

--- 5.2 Session Lifecycle ---

session_status enum values:
  - pending
  - accepted
  - active
  - pending_review
  - completed
  - cancelled

Typical flow:
  1. REQUEST    — Learner creates pending session; duplicate open sessions prevented
  2. ACCEPT     — accept_session RPC: escrow learner credits, store meet_link
  3. ATTEND     — record_session_join / record_session_leave track seconds
  4. ACTIVE     — Session in progress; messaging allowed when active
  5. REVIEW     — move_due_sessions_to_review; pending_review status
  6. SETTLE     — auto_settle_session, complete_session; attendance-based outcomes
  7. COMPLETE   — Credits released or refunded; reviews; terminal status

Key RPCs (examples):
  - accept_session, reject_session, cancel_session
  - complete_session, auto_settle_session, dispute_session
  - record_session_join, record_session_leave, session_attended_seconds
  - move_due_sessions_to_review, settle_pending_review_sessions
  - propose_reschedule, accept_reschedule, reject_reschedule, withdraw_reschedule

--- 5.3 Credit & Escrow Model ---

Before escrow (legacy):
  Credits moved only on complete_session() — teacher could be ghosted.

After escrow migration (20260508050000_session_escrow.sql):
  - credits held when teacher ACCEPTS (escrow_held = true on sessions)
  - Completion releases escrow to teacher
  - Cancellation refunds learner
  - credit_transactions ledger records holds, releases, refunds
  - Client direct writes to credits/session status LOCKED via later migrations

Settlement (20260512060000_session_review_and_settlement.sql):
  - Attendance-based partial splits
  - session_settlement audit table
  - Outcomes: full pay teacher, partial split, full refund, no-show rules
  - Terminal status: completed if teacher paid, cancelled on full refund

Finance admin:
  - request_finance_action / approve_finance_action (maker-checker)
  - run_finance_reconciliation, create_finance_report_manifest

--- 5.4 Trust & Safety ---

  - user strikes and suspension (user_active_strike_weight, user_suspension_state)
  - my_strike_summary RPC for UI (StrikeBanner component)
  - admin_issue_strike, admin_revoke_strike

--- 5.5 Availability & Matching ---

--- 5.6 Learning Tracks ---

--- 5.8 Enterprise Admin (phased migrations) ---

Phases in migration filenames (20260511070000 through 20260511130000+):

  Phase 1 — Enterprise admin foundation
  Phase 2 — Audit and security dashboards
  Phase 3 — Cases and access governance
  Phase 4 — Finance (wallet, reconciliation)
  Phase 5 — Privacy and compliance (GDPR-style requests, retention)
  Phase 6 — Settings and change management (propose/approve/publish)

Capabilities include:
  - RBAC: domain:action permissions (get_my_admin_permissions)
  - Admin cases from reports (admin_cases, notes, SLA)
  - JIT admin access requests (request_admin_access, approve/reject)
  - Break-glass emergency access with expiry and ticket reference
  - Audit event chain (get_admin_audit_events, verify_admin_audit_chain)
  - Feature flags in database (get_admin_feature_flags)
  - PII reveal controls (reveal_admin_user_pii)
  - Privacy export/anonymization/retention purge RPCs
  - System health dashboard
  - Admin broadcast notifications

RBAC documented in: docs/compliance/rbac-sod-model.md

Permission format: domain:action

Domains:
  moderation, users, sessions, wallet, analytics, compliance, settings,
  incident-response, access-governance, security, privacy

Actions:
  read, create, update, approve, export, override, reveal, delete

Role templates:
  moderator          — Report queue, limited context
  trust_lead         — Escalation, export capability
  finance_ops        — Wallet/escrow; maker-checker for high-risk
  compliance_auditor — Read/export only at runtime
  super_admin        — Platform admin; maps from profiles.is_admin
  break_glass        — Emergency only; expiry + incident ticket required

8. SECURITY ENGINEERING
================================================================================

--- 8.1 Edge Security (server.ts) ---

Custom Cloudflare Worker wraps TanStack Start default handler.

Headers injected on every response:
  - Content-Security-Policy (detailed multi-directive policy)
  - X-Frame-Options: DENY
  - X-Content-Type-Options: nosniff
  - Strict-Transport-Security: max-age=31536000; includeSubDomains
  - Referrer-Policy: strict-origin-when-cross-origin

CSP highlights:
  - frame-ancestors 'none'
  - default-src 'self'
  - script-src: self, unsafe-inline (Vite HMR, theme script, charts tradeoff),
                8x8.vc, meet.jit.si, Turnstile, hCaptcha
  - style-src: self, unsafe-inline, hCaptcha
  - img-src: self, data, blob, *.supabase.co, googleusercontent, hCaptcha
  - connect-src: self, *.supabase.co, wss://*.supabase.co, generativelanguage.googleapis.com,
                 accounts.google.com, CAPTCHA hosts
  - frame-src: self, Jitsi, CAPTCHA iframes
  - object-src 'none'
  - base-uri 'self'
  - form-action 'self', accounts.google.com
  - upgrade-insecure-requests

Rationale: Supabase auth tokens in localStorage — XSS is high impact; CSP mitigates.

--- 8.2 Database Security (migration themes) ---

  - Lock direct client UPDATE on credits, escrow, session status
  - Lock message, review, notification client writes to RPCs only
  - Revoke unused admin RPC access from anon/authenticated where inappropriate
  - hide_public_credits migration
  - Harden report creation
  - lock_is_admin_to_self
  - lock_messages_to_active_sessions
  - report_evidence_snapshots
  - lock_sweep_rpcs_to_service_role (cron-style functions)
  - enterprise admin audit chain verification

--- 8.3 Auth & Session Hygiene ---

  - scrubLocalCaches() on SIGNED_OUT — removes skillswap-* keys from storage
  - Prevents avatar/credit/profile leaks on shared devices
  - exchangeAuthCodeFromUrl for email verification redirects

14. ENGINEERING THEMES & PROJECT SCALE INDICATORS
================================================================================

1. Database as source of truth
   - 110 migrations; business logic in RPCs, not a separate REST API

2. Security-first edge
   - Custom Worker with documented CSP for every third-party origin

3. Enterprise admin
   - RBAC, SoD, maker-checker finance, audit chain, privacy requests
   - Unusual depth for a student innovation project

4. Optional intelligence
   - Gemini suggestions grounded in real DB data (anti-hallucination design)

5. Realtime product feel
   - Banners and toasts for sessions, messages, calls, credit updates

6. Compliance awareness
   - Runbooks for audit, retention, RBAC, change management

Scale indicators:
  - 24 routes
  - ~75 components
  - ~24 lib modules
  - 110 SQL migrations
  - 80+ database RPCs in generated types
  - 3 Edge Functions + shared CORS
  - 6 compliance documents

15. WHAT THIS PROJECT IS NOT
================================================================================

  - NOT a traditional REST API backend — API is Supabase Postgres RPCs + RLS
  - NOT payment-processor integrated for core flows — credits only
  - NOT a monorepo with multiple apps — single application folder
  - NOT a mobile native app — responsive web (PWA-capable meta tags)

16. DEVELOPMENT WORKFLOW
================================================================================

Prerequisites:
  - Node.js (for npm)
  - Supabase project (URL + anon key in .env)
  - Optional: Supabase CLI for migrations and Edge Functions
  - Optional: Cloudflare account for Workers deploy

Local development:
  1. Copy .env.example to .env and fill Supabase variables
  2. npm install
  3. npm run dev
  4. Open Vite dev server URL

Production build:
  npm run build
  Deploy via Wrangler to Cloudflare Workers

Database:
  Apply migrations with Supabase CLI: supabase db push (or linked project workflow)

Edge Functions:
  Deploy with Supabase CLI; set secrets for GEMINI, JAAS, N8N

Tunnel testing:
  vite.config.ts allows ngrok and trycloudflare hosts for OAuth/CAPTCHA testing
